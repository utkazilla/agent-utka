# Подготовь документ для Agent Utka

Изучи текущий проект и собери один Markdown-файл, по которому помощник сможет отвечать на вопросы во время звонка и точно писать названия из кода в расшифровке. Работай в пределах выбранного проекта и доступных тебе материалов. Сохрани результат в `utka-cue-knowledge.md` в корне проекта в кодировке UTF-8. Уложись в 180 000 байт. При повторном запуске обнови этот файл под тем же именем.

## Что изучить

1. Определи границы проекта и назначение его основных модулей по README, архитектурным документам и точкам входа.
2. Проследи важные рабочие сценарии по коду, API-контрактам и тестам. Найди условия, ограничения, статусы, ошибки и исключения, о которых спрашивают на звонках. Отделяй действующее поведение от требований, планов и исторических решений.
3. Собери важные имена из кода и документации. Ищи названия сервисов и интеграций, сокращения предметной области, поля, параметры, коды статусов, заголовки и имена методов, которые произносят вслух. Запиши точное написание и понятное русское значение каждого важного имени.
4. Сверь каждый существенный факт с источником. Указывай относительный путь и строку, например `src/...:42`. Для переданного внешнего документа укажи его название, раздел и ссылку, если она доступна. При расхождении между источниками укажи, что подтверждает каждый из них. Вынеси сведения, которые ещё нужно проверить, в отдельный раздел.

Используй только материалы, которыми можно поделиться с получателями файла. Не включай секреты, токены, содержимое переменных окружения, персональные данные, сырые логи и расшифровки звонков. Пропусти игнорируемые и служебные файлы, артефакты сборки и зависимости. Перед сохранением проверь документ на случайно скопированные чувствительные значения.

## Как оформить документ

Начни с названия проекта. Укажи дату проверки и ревизию, если проект хранится в Git. Дальше используй такие разделы, опуская те, для которых нет материала.

- **Проект и модули**. Кратко объясни назначение проекта и границы ответственности модулей.
- **Рабочие сценарии**. Опиши шаги, условия и результаты. Сохраняй различия между похожими состояниями, ветками и исключениями.
- **Вопросы на звонке**. Для важных вопросов напиши по одному прямому ответу и укажи источник. Держи ответ, условия его применимости и ссылку рядом, чтобы фрагмент можно было найти и процитировать отдельно.
- **Словарь**. Запиши точные имена, русские значения и источники. Для поля или статуса поясни, где его встретить и что оно означает в этом контексте.
- **Что проверить**. Отметь вопросы, по которым подтверждения пока нет.

Пиши короткими самостоятельными абзацами. Вставляй имена из кода с исходным регистром, дефисами и подчёркиваниями. Если источники используют разные имена для разных сущностей, сохрани это различие. У каждого названия и числа должен быть понятный контекст.

## Словарь для распознавания речи

В конце файла добавь один блок с меткой `utka-cue-asr`. Внутри должен быть валидный JSON без комментариев и замыкающих запятых. Значения и источники держи в обычном тексте документа.

- `terms` содержит до 200 уникальных канонических написаний длиной до 120 символов каждое.
- `hotwords` содержит до десяти наиболее важных имён из `terms`. Подбери их по частоте и важности для звонков.
- `aliases` содержит до 200 правил. Каждое правило связывает имя из `terms` со списком `heard` из одного–шестнадцати вариантов. Укажи вероятные произношения по буквам, русскую транслитерацию и разбивку составных имён, если связь однозначна. Добавляй наблюдаемые ошибки распознавания, когда они есть в переданных примерах. Варианты произношения в этом блоке служат подсказками для распознавания.
- Для неоднозначного варианта добавь отдельное правило с `context`. Используй короткие слова или фразы из соседнего текста. Варианты можно разделить знаком `|`, как в `"поле|идентификатор задания"`. Например, можно потребовать упоминание поля, статуса или конкретной операции. Общие слова и произношения, подходящие к нескольким именам, оставь без автоматической замены, если их нельзя различить по контексту.
- Проверь, что варианты для разных имён не конфликтуют. Указывай более длинные составные варианты раньше коротких. Если надёжных вариантов нет, можно оставить `aliases` пустым.

Ниже показана структура блока на вымышленном примере. В итоговом документе замени пример именами из текущего проекта.

```utka-cue-asr
{
  "terms": ["syncJobId"],
  "hotwords": ["syncJobId"],
  "aliases": [
    {"term": "syncJobId", "heard": ["синк джоб ай ди", "sync job id"]},
    {"term": "syncJobId", "heard": ["джоб айди"], "context": "синхронизац"}
  ]
}
```

Перед завершением перечитай файл. Убедись, что в нём нет неподтверждённых ответов, что указанные пути ведут к источникам, а каждое имя из `hotwords` и `aliases` есть в `terms`. Сообщи путь к готовому Markdown-файлу.
